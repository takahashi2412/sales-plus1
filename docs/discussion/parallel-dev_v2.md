## 1. 前回（v1）で決まったこと

本人が記録に残した結論です（まだ CLAUDE.md の規則には入れていない）。

1. 並列はエージェントごとに別のワークツリー・別のブランチ。「1つの計画ファイル＝1つのブランチ＝1つの報告書」のまま、Claude Code が1本ずつレビューする
2. E（土台）と A の表（データ）は1本ずつ。並列の前に、共通の部品（左メニュー・画面の枠・共通の型・パッケージ）まで1本で作る
3. A の画面は2本で並列：「記録の画面＋テーマ表と卒業の知らせ」と「トーク一覧」
4. 最初は並列2本まで。2本とも本線に取り込むまで、次の並列は始めない
5. 計画ファイルに「触ってよいファイル・フォルダ」を書く。報告書に「本人が画面で確かめる手順（3〜5行）」を足す
6. 最初の1画面でデザインのお手本を固めてから並列にする
7. A の画面の直前に、ワークツリーの動きをこのPCで小さく1回試す
8. サブエージェントより、Claude Code が計画ファイルを2本作って別々に動かす

## 4. 論点

### 論点1：この順番でよいか

- 上の8周の順番に賛成か。入れ替えたほうがよい所はあるか
- 本人に早く価値を見せるには、どの周を前に出すべきか（たとえば KPI とカルテを早める）

### 論点2：集める画面（ホーム・ダッシュボード・カルテ）をいつ作るか

- 案A：各周で少しずつ育てる（例：周2でカルテに「ロープレ」だけ出す、周3で KPI を足す）。早く見せられるが、毎周カルテを触るので並列の邪魔になる
- 案B：周6のあとにまとめて作る。並列はしやすいが、カルテ（このアプリの中心）を見せるのが遅くなる
- どちらがよいか。別の案があれば

### 論点3：アプリ全体で並列にできる組・できない組

- 上の表で「2本」とした組（KPI と部下メモ、週間教育と研修、自動化と過去の記録）は本当に並列にできるか
- ほかに並列にできる組、逆に並列にすべきでない組はあるか

### 論点4：途中で止めて確かめる所

- 本人が触って確かめる（使ってみる）のは、どの周の終わりがよいか（全部の周か、まとまった周だけか）
- 設計を見直すかもしれない危ない所（例：一般日報は欄が多い、AI は判定の計算が難しい）はどこか

## 2. 論点と Claude Code の考え

### 論点1：並列は、このPCでどう動くか

聞きたいこと：
- Antigravity で複数のエージェントを同時に動かすとき、各エージェントは別のフォルダ（ワークツリー）・別のブランチで作業するのか、同じフォルダか
- 同じファイルを2つのエージェントが同時に書き換えないために、どんな仕組み・決まりが要るか
- 各エージェントの作業結果を、どうまとめて本線に出す想定か（Claude Code がレビューしてから本線に取り込む今の流れと合うか）
- 上のうち、この環境（このPC）で実際に確かめたこと／確かめていないこと

Claude Code の考え：
- 並列にするなら、エージェントごとに別のワークツリーと別のブランチ（例：`task/roleplay-screen`、`task/talk-list`）で作らせ、同じフォルダで同時に書かないのが前提
- 作業の結果は、今と同じく Claude Code が1本ずつレビューし、本人のOKのあとに本線へ取り込む

### 論点2：E と A のどこを並列にするか

判定ルール（3つとも「いいえ」のときだけ同時に進める）：
1. ほかの作業の結果が要るか → はいなら順番に
2. 同じファイルを触るか → はいなら1つにまとめる
3. 1つの変更として一緒に出すか → はいなら1つにまとめる

Claude Code の仕分け：

| 作業 | 並列 | 理由 |
|---|---|---|
| E 土台（ログイン・名簿・権限・守りのテスト） | しない（1本） | ほかの全部がこの結果を使う |
| E を Supabase と Firebase の2案で同時に作って比べる | できる | 別のフォルダで、互いの結果が要らない。ただし本人は Supabase を選択済み |
| A：ロープレの表（データ） | しない（先に1本） | 画面がこの表を使う |
| A：記録の画面／テーマ表と卒業の知らせ／トーク一覧 | できる（表のあと） | 別の画面・別のファイルで、別々に確かめられる |

聞きたいこと：この仕分けに賛成か。ほかに並列にできる・すべきでない所はあるか。

### 論点3：レビューと確認の量をどう抑えるか

Claude Code の考え：
- 並列にすると作るのは速くなるが、Claude Code のレビューと本人の確認も同時に増える。並列の数は、本人が確かめられる量に合わせる（最初は2本まで）
- 各エージェントの報告書に「変更したファイル・テストの結果・決められずに止めたこと」を必ず書かせ、レビューを短くする

聞きたいこと：並列の数の目安、レビューを楽にする工夫、並列にしたときに起きやすい失敗。

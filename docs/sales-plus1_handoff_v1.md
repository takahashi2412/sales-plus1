# SALES +1 引き継ぎ資料（v1）

作成：2026年10月6日（火） ／ 作成元：Claude.ai チャットでの企画・設計の壁打ち
用途：Claude Code で本格開発を始めるにあたり、ここまでの決定事項・設計・未決事項をすべて引き継ぐ

## 1. 一言でいうと

営業部でバラバラに（主にExcelで）管理している6つの業務を1つのWebアプリに統合し、**メンバー1人ひとりを「カルテ」で一元把握**できるようにする。さらに **KPIをAIが分析し、改善提案と週次の取り組みまで出す仕組み**を組み込む。

- 目的の最優先：**部下の状況を人単位で一元把握すること**
- 将来の発展：KPI分析 → AIによる改善提案 → 実行 → 効果検証のループ

## 2. 名前（確定）

| 場面 | 表記 |
|---|---|
| アプリ名・ロゴ・画面 | **SALES +1**（読み：セールスプラスワン） |
| スローガン | **1DAY +1** |
| URL（Firebase想定） | sales-plus1.web.app（取れなければ予備：rushup-sales-plus1） |
| GitHubリポジトリ | sales-plus1 |
| ファイル名・フォルダ名 | sales-plus1_〇〇 |

- 由来：Rush up に毎日・毎週「＋1」を積む
- ドメインやID類には「+」が使えないため、技術的な識別名は sales-plus1 に統一
- 仕組みの中での言葉の使い分け：
  - 毎日の入力・アラート → 「今日の+1」（1日の行動で積む）
  - 週次AIレポート → 「今週の+1」（AIが提案する改善）
  - カルテの成長記録 → 「積み上げた+1」（過去の取り組みと効果）
- URLを伝えるときは「最後は数字の1」と添える（l との誤読防止）
- 将来、営業部以外（制作・MEO運用など）に広げる場合は「RUSH +1」へ拡張する余地を残す

## 3. 前提・背景

- 現状：6業務とも**主にExcel/スプレッドシート**で管理
- 既存の営業管理プラットフォーム（rushup-weekly-report、React + Vite + Firebase）とは**別アプリとして新規作成**する
- **日々のKPI入力は新アプリに一本化**する。既存プラットフォームにも日次KPI入力（6指標×11時間帯＋承認フロー）が設計されているが、二重入力を防ぐため新アプリ稼働後は既存側のKPI入力は使わない運用にする
- 既存側の時間帯別KPIのデータ構造の考え方は流用してよい

## 4. 対象業務（6つ）

| 区分 | 業務 | 入力者 | 頻度 |
|---|---|---|---|
| 定量（結果） | 日々のKPI（**時間帯別**） | メンバー | 毎日・時間帯ごと |
| 定性（本人） | 一般日報 | メンバー | 毎日 |
| 定性（管理） | 責任者日報 | リーダー／MGR | 毎日 |
| 指導記録 | 部下メモ | リーダー／MGR | 随時 |
| 指導記録 | ロープレ管理 | リーダー／MGR | 随時 |
| 育成計画 | 週間教育 | リーダー／MGR | 週次 |

すべての記録は「**メンバーID × 日付 × 記入者**」で紐づく。

## 5. 中心コンセプト：メンバーカルテ

1人のメンバーを開くと、以下が1画面で見える。

1. 基本情報（チーム・役割・入社日・担当リーダー）
2. 今週のKPIサマリー（前週比・目標進捗）
3. KPIの週次推移グラフ。**面談・ロープレ・教育の実施日を縦線マーカーで重ねる**（指導前後の数値変化を視覚化）
4. 時間帯別のKPI（例：接続率）。弱い時間帯を強調
5. タイムライン：日報・責任者日報（言及分）・部下メモ・ロープレ・週間教育・AI提案を**日付順に混在表示**、種類で絞り込み可能

統合の価値：「日報で数値低下 → ロープレで該当項目が低い → 今週の教育テーマに反映 → 数値が回復」という因果を1画面で追える。

| members | 氏名、チーム、役割、入社日、担当リーダー | 名簿シート |
| kpi_entries | メンバー、日付、時間帯、指標ごとの数値 | KPIシート |
| kpi_targets | メンバー（またはチーム）、期間、指標、目標値 | 目標設定 |
| daily_reports | メンバー、日付、所感・振り返り | 日報シート |
| manager_reports | 記入者、日付、チーム状況、対応事項、**言及メンバー（複数）** | 責任者日報シート |
| subordinate_memos | 対象者、記入者、日付、**種別タグ**、内容 | メモシート |
| roleplays | 対象者、評価者、日付、**固定評価項目ごとのスコア**、コメント | ロープレ評価シート |
| trainings（週間教育） | 対象（個人 or チーム）、週、テーマ、**狙うKPI指標**、実施状況、振り返り | 教育計画シート |
| ai_reports | 対象者、週、版（本人版／指導版）、本文、生成日時 | （新規） |

| alerts | 対象者、日時、条件、内容、**対応結果（対応済／不要だった）**、理由 | （新規） |

### 6-2. 必ず入れる設計（後からでは取り返しがつかないもの）

- **週間教育に「狙うKPI指標」欄**：取り組みとKPIを紐づけ、効果をプログラムで機械判定するため。最重要
- **ロープレは評価項目を固定したスコア形式**（例：ヒアリング／切り返し／クロージング、5段階）。自由記述だけにしない
- **部下メモに種別タグ**（例：面談・モチベーション・スキル課題など）
- **責任者日報に「言及メンバー」タグ**：チーム単位の記録を個人カルテにも自動表示するため
- AI提案の**採用／却下の記録と却下理由**：採用率の集計と提案精度の改善に使う

## 7. 日々のKPI（時間帯別）

- 粒度：**時間帯別**（既存プラットフォームと同じ粒度）
- 指標名・時間帯の区切りは**未確定**（現行Excelの提供待ち）。モックでは仮に「架電数・接続数・アポ数／接続率・アポ率（対接続）」「9時〜19時の11区分」としている
- 入力UXの方針：
  - 終業後にまとめて入れさせない（負担と精度低下を防ぐ）
  - **今の時間帯の行だけが開いた状態**で表示し、各時間帯の終わりに数秒で入力
  - スマホから入力可能に
  - 日次合計・率・達成率は自動計算
  - **KPI入力と一般日報は1画面にまとめる**（上半分KPI、下半分所感）。データは別テーブル
- 承認フローの要否は未確定（既存側にはMGR承認フローあり）

| ロール | 主な権限 |
|---|---|
| 経営（代表） | 全体閲覧 |
| MGR | 全チーム閲覧、指導記録の入力、AI指導版の閲覧 |

## 9. AI分析の仕組み

### 9-1. 週次サイクル

| 工程 | 担当 | 内容 |
|---|---|---|
| ① 集計・検知 | **プログラム** | 時間帯別KPIから率、前週比、チーム平均との差、時間帯別の落ち込みを計算し異常値を抽出 |
| ② 原因分析 | AI | ①の数値に、ロープレ項目別スコア・部下メモ・日報・責任者日報を突き合わせて仮説を出す。**仮説ごとに根拠にした記録を明示** |
| ③ 改善提案 | AI | メンバーごとに今週の取り組み（教育テーマ・ロープレで見る項目）を、狙うKPI・期間・効果判定日付きで提案 |
| ④ 判断 | リーダー／MGR | 採用／修正して採用／却下 → 週間教育に登録 |
| ⑤ 効果検証 | プログラム＋AI | 取り組みの狙うKPIが動いたかを判定（**同期間のチーム平均と比較**して本人だけが動いたかを見る）。次の提案に反映 |

原則：**数値計算はプログラム、解釈と提案はAI**。AIには計算済みの正確な数値だけを渡す。

### 9-2. レポートは2種類（確定：本人にも見せる）

| 区分 | 閲覧者 | AIに渡すデータ | トーン |
|---|---|---|---|
| 本人版 | メンバー | KPI・自分の日報・ロープレ結果**のみ** | 伸びたところから始め、次の一手を行動ベースで1つに絞る |
| 指導版 | リーダー／MGR | 上記＋部下メモ・責任者日報 | 原因仮説と指導の打ち手 |

- **本人版には部下メモを「渡さない」**（プロンプトで「触れるな」と指示する方式では漏れを防ぎきれないため、データ段階で分離する）
- 本人版は評価・叱責に読めない書き方に統一（×「アポ率が低い」 ○「15時台の名乗りを短くすると伸びしろが大きい」）
- 本人版の最後に「今週、自分で意識すること」を書いてリーダーに共有する欄
- 生成タイミング：毎週月曜朝に自動生成

### 9-3. 日次アラート（確定：週次＋日次）

- 判定は**AIではなくプログラムの閾値判定**（速く確実に）
- 時間帯別KPIを活かし、**当日の途中で検知**（例：午前の架電数が本人平均を大きく下回る、接続が続いているのにアポが連続ゼロ）
- 通知先は**リーダー向けのみ**。本人は週次レポートで振り返る（監視感を避ける）
- 最初は条件を2〜3種類に絞る。リーダーが「対応済／不要だった」を押せるようにし、不要率の高い条件を調整

### 9-4. 自動化レベル（未決定・推奨案あり）

- 推奨：**「AIは提案まで、登録は人が判断」から開始** → 提案の採用率が一定水準を1か月続けて超えたリーダー（チーム）から「承認で自動登録」に移行する段階方式
- 採用率・却下理由はデータとして残す

## 10. 段階導入

| 段階 | 内容 | 狙い |
|---|---|---|
| 第1段階 | メンバーマスタ＋部下メモ＋ロープレ（リーダー層で開始）。**KPIは当面Excel入力を続け、CSVで取り込んでカルテに表示** | 現場の入力習慣を変えずに、初日から「指導記録と数値が並ぶカルテ」を使える。過去KPIがあるのでAI機能も早めに試せる |
| 第2段階 | KPI（時間帯別）と一般日報の入力をアプリに切り替え | 全員の入力が変わる最大の移行なので、カルテの価値が伝わった後に行う |
| 第3段階 | 責任者日報と週間教育 | — |
| AI | まず①検知と②③の提案レポート。⑤効果検証ループは取り組みデータが蓄積してから | — |

既存のExcelデータはCSVで一括取り込みし、過去履歴もカルテに表示する。

## 11. モック（作成済み）

デザインキャンバス：https://claude.ai/artifact/P4LCaBUUUe9KogUY8cBWZ4 （サンプルデータ）

1. **メンバーカルテ（リーダー・MGR画面）**：左メニュー（ダッシュボード／メンバーカルテ／KPI・日報入力／責任者日報／部下メモ／ロープレ／週間教育／AIレポート）、KPIタイル4つ、アポ率推移＋指導マーカー、時間帯別接続率、タイムライン（部下メモに「本人には非表示」表示）
2. **AI週次レポート 指導版**：結論 → ①数値の検知（表） → ②原因の仮説（根拠記録付き、確度表示） → ③今週の取り組み提案（採用／修正して採用／却下ボタン、狙うKPI・期間・効果判定日） → ④過去の取り組みの効果（チーム平均比較） → ⑤今週の日次アラート（対応結果つき）
3. **AI週次レポート 本人版（スマホ 390px幅）**：伸びたところ → KPI3つ → 次の一手（時間帯グラフ） → 今週の取り組み → 自分で意識すること（共有ボタン）。部下メモ由来の内容は出さない

まだモックがない画面：KPI・日報入力画面、ダッシュボード（チーム一覧）、各入力画面

## 12. デザイン指針（Rush up 資料デザインに準拠）

デザインシステム：「Rush up 資料デザイン」https://claude.ai/artifact/7RxJZaSDarmXm2KAcUQE6E （アプリはパターンA スタンダード）

- 合言葉：「結論から、数字で、ひと目で」
- 色：ロゴの赤 `brand` #FF0642（塗り）／文字の赤 `brand-strong` #CC003A／濃紺 `navy` #002459（構造：表見出し・番号・ボタン）
- **赤は1画面1〜2か所**（結論・いちばん伝えたい数字だけ）
- 状態色：達成 `good` #047857（▲）、要注意 `warn` #B45309、**未達は赤にしない**（黒字＋▼＋「未達」）
- 淡色：`brand-soft` #FFE4EA（結論枠）、`navy-soft` #E6EBF4、`warn-soft` #FEF3E2、`good-soft` #E3F4EC、`bad-soft` #E8E8EA
- 地 `paper` #F7F7F8、面 `surface` #FFFFFF、罫線 `line` #DDDDDD、文字 `ink` #1A1A1A、注釈 `ink-muted` #555555
- 書体：見出し Yu Gothic 太字、本文 Yu Gothic Medium（Windowsで細く見えないよう必須）、数字 Segoe UI
- 余白は 4/8/12/16/24/32/48/64px の8段。角丸 4px（タグ）／8px（カード）／999px（丸番号）。影は使わない
- 増減は「前週 6.1% → 6.8%」の形で▲▼を必ず付ける。色だけで良し悪しを伝えない
- 絵文字は使わない
- グラフ：本人＝brand、比較対象＝chart-muted #C8C8CC、目盛りは0から

## 14. 開発上の注意

- **社員の実名と人事評価を含むデータは、リポジトリやWorkspaceに置かない**。リポジトリにはサンプルデータのみ。実データはDB側で管理
- APIキー等は .env に置き、コミットしない
- 本人版レポート生成時は、部下メモ・責任者日報をAIへの入力から**コード上で除外**する（テストで担保する）
- アプリの文言・UIはすべて日本語

## 1. 目的（なぜやるか）
電話システムのCSVを業後に1回取り込んで承認し、日報の前に数字を確定させる。本人が月初に立てたKPIの目標から日次・月次の目標を自動で出し、承認の直後に、目標に届かなかった人の一覧をリーダーの画面に出す（設計書3・3-2・11章。まとまり4）。

## 2. やること
先に計算の部品とテスト（1）を作って通してから、画面（2〜4）を作る（設計書13章「危ない所と備え」：集計のルールは計算だけの部品を分け、架空データの自動テストを画面より先に通す）。

1. 計算の部品（`src/features/kpi/shared/`。画面やデータベースに頼らない関数にする）とテスト（`tests/kpi/`）
   - CSVの読み取り：Shift_JIS を `TextDecoder('shift_jis')` で読む（ライブラリは足さない）。1行目＝期間と略号の説明、2〜3行目＝見出し2段（時間帯14区分×総・実・再・オ・見・ア）、4行目から＝1人1行（1列目が名前）、最後の行＝合計（1列目が「合計」。取り込まない）。1行は 85列（名前1列＋14区分×6項目）。時間帯の見出しは左から `0:00〜8:59`・`9:00`〜`20:00`・`21:00〜23:59`（4章の `time_slot` に対応づける）
   - チーム名と日付：チーム名はファイル名の「時間別」より前の部分（例：`zoom(WEB)時間別20261006_20261006….csv` → `zoom(WEB)`）。日付は1行目の期間（例：`2026年10月06日〜2026年10月06日`）から読む。ファイル名に日付があれば、1行目と同じかも確かめる
   - 取り込みのチェック（設計書9章「CSV取り込み・承認」の5つ）：①期間が1日だけか ②見出しの形が同じか（電話システムの画面が変わったことに気づくため）③名前が対応表にあるか（`cti_member_map` の有効期間の中で。`member_id` が空の名前は「取り込まない」として飛ばす）④項目ごとに、人の行を足すと合計の行と合うか ⑤同じ日・同じチーム名の取り込みがもうあるか（あれば置きかえの確認を出す）。①②④が合わないときと、③で対応のない名前が残っているときは取り込めない。ほかに、名簿の今の所属と、CSVのチーム名の対応（`cti_team_map`）のチームが食い違う人は警告として出す（止めない）。同じ人が同じ日のほかの承認済みの取り込みにいるときは承認できない（データベースも止める）
   - 目標の逆算（設計書3-2「月初の目標の立て方」。今のKPIブックと同じく、途中で丸めず小数のまま計算する。画面の表示は小数第1位まで）
     - 行動の目標：総（日次）＝1日のコール時間×ターム。総（月次）＝総（日次）×稼働日。実・再・オ・見（日次・月次）＝総×それぞれの率の目標。ア/オの目標＝`rate_apo_owner`
     - 成果の目標（営業に出る人）：件数＝目標粗利÷単価、受注（KGI）＝件数÷完了率、採用・訪問＝受注÷受注率、ア（月次）＝採用・訪問÷採用率。架空の例：320P÷40P＝8件、÷80%＝10件、÷25%＝40件、÷80%＝50件
     - 営業に出ない人（アポだけの人）：ア（月次）＝本人が入れたアポの目標件数（`apo_target`）、採用（月次）＝ア×採用率。粗利・受注の目標は持たない（設計書3-2 v21）
     - 「総×オ率×ア/オから出るアポ数（月次）」も並べて出し、ア（月次）と合わないときは画面で知らせる
   - 営業日：その月の日のうち、土日と、設定値 `kpi_holidays`（`settings`。祝日と会社の休みの日の一覧）にある日を除いた日（2026-11-05 本人の選択）。設定値がないときは土日だけを除き、画面に「会社の休みの日が設定されていません」と出す
   - 未達の判定（設計書11章・まとまり4。2026-11-05 本人の選択を含む）：
     - 日ごと：対象の日が営業日で、その日の総が1以上の人だけ（総が0の日＝休みの日は日ごとの未達を出さない。休んだ分は月のペースに出る）。総・実・オは「その日の実績 < 日次の目標」、ア/オは「その日のア÷オ < ア/オの目標」（オが0の日はア/オを判定しない）。日ごとの未達は、いつも対応を求める（`needs_response` を真）
     - 月のペース：総・実・オ・ア・ア/オ。あるべき＝月次の目標×その月の1日から対象の日までの営業日の数÷その月の営業日の数。実績は、その月の1日から対象の日までの承認済みの日々のKPIの合計（ア/オは、合計のア÷合計のオ）。「実績 < あるべき」なら未達。**対応を求めるのは新しく遅れた日だけ**：その月の最初の営業日か、ひとつ前の営業日の時点では遅れていなかったとき（ひとつ前の営業日の時点も、同じ計算で出し直して比べる）。遅れが続いている日は、`needs_response` を偽にして一覧に「続いている」と並べる
     - 目標が未入力：その月の目標（`kpi_targets`）がない人は `target_missing` を1つ出す。対応を求めるのは、その月でその人の承認済みの日々のKPIがはじめて出た日だけ
     - 採用・訪問件・受注は判定しない（日報で入力するので、一般日報の区切りで足す）
   - テスト（`tests/kpi/`。架空の名前と数字だけ）：CSVの読み取り（架空のCSVを Shift_JIS で作って置く。作り方は下）、5つのチェックの合う・合わない、上の架空の例の逆算、営業に出ない人の逆算、営業日（土日・休みの日・月またぎ）、日ごとの未達（総が0の日・オが0の日を含む）、月のペースと「新しく遅れた日」、目標が未入力、月の途中で異動した人（所属の食い違いの警告）
   - 架空のCSV（Shift_JIS）の作り方：PowerShell の `[System.Text.Encoding]::GetEncoding(932)` で書き出して `tests/kpi/fixtures/` に置く（画面で試す見本は `fixtures/kpi/sample-csv/` にも置く）。名前は土台の架空の人の名前か「架空〇〇」だけ。作り方を報告書に書く
2. CSV取り込み・承認の画面（`src/features/kpi/import/`。左メニューの「CSV取り込み」＝管理者の権限がある人だけ）
   - ①ファイルを選ぶ（1日に2〜3ファイルをまとめて選べる。1ファイル＝1つの取り込みの記録）→ ②チェックの結果を出す（ファイルごとに：日付・チーム名・人数・項目ごとの合計・合計の行と合うか・対応のない名前・所属の食い違い・同じ日の取り込みがあるか）→ ③対応のない名前を名簿の人に結ぶか「取り込まない」にする（`cti_member_map` に足す。`valid_from` は対象の日。次回から自動）。CSVのチーム名が対応表にないときは、アプリのチームを選んで `cti_team_map` に足す → ④取り込む（承認前。数字は取り込んだ人にだけ見える）→ ⑤承認する（承認の直後に1の計算で未達を出し、`alerts` に入れる。入れた件数を出す）
   - 同じ日・同じチーム名の取り込みがあるときは「置きかえますか」の確認を出し、①plan_kpi-memo-common_v1 の4章「取り込み直すときの流れ」の順に行う（前の記録を置きかえ → 新しい記録 → 日々のKPI → 承認 → 未達を出し直す）。前の数字とアラートは消さない
   - 承認前の取り込みは、承認せずに置きかえて取り消せる（`status` を `replaced` に）
   - 取り込みの記録の一覧（日付・チーム名・人数・状態・取り込んだ人・承認した人）と、名前の対応・チーム名の対応の一覧（有効期間の終わり `valid_to` を入れて使わなくできる。削除はしない）
3. KPIの目標の画面（`src/features/kpi/targets/`。左メニューの「KPIの目標」＝だれにでも）
   - 自分の目標：今月と来月の目標を入れる・直す。名簿の「営業に出る／出ない」で欄を出し分ける（出る人＝目標粗利・単価・完了率・受注率、出ない人＝アポの目標件数。どちらも稼働日・1日のコール時間・ターム・実率・再率・オ率・見率・ア/オ・採用率）。入れながら、1の逆算で月次・日次の目標を並べて出す
   - 月が始まってから直すと「修正あり」の印がつき、前の値の控え（`history`）が残ることを画面に書く（2026-11-05 本人の選択）。直した記録は「いつ・どの欄が・前の値→今の値」で見られる
   - 上席（リーダー・担当MGR・代表）と管理者の権限がある人：読める人の目標を、人を選んで見る（入力はできない）。今月の目標の状態（入力済み／未入力／修正あり）を人ごとに並べる
4. 未達の一覧の画面（`src/features/kpi/alerts/`。左メニューの「未達の一覧」＝リーダー・MGR・代表）
   - 日付ごと（新しい日が上）に、人ごとの未達を並べる：項目・比べ方（日ごと／月のペース）・目標（またはあるべき）・実績・差。未達は黒字＋▼＋「未達」（赤にしない）。月のペースで遅れが続いている行は「続いている」と出し、対応の欄を出さない。目標が未入力の人は「目標が未入力」
   - リーダー（その人と今同じチーム）は、対応を求める行に「対応済」「不要だった」と理由（必須）を入れる。MGR・代表は見るだけ（担当MGRも同じ一覧を見られる。設計書11章）
   - 未対応の数を一番上に出す。日付とチームで絞り込める
   - メンバー本人には出さない（左メニューにも出ない。データベースも読ませない）

### 安全の決まり（2026-10-28 本人の選択）
- 表を足すときは、マイグレーションの中で RLS（行ごとの読み書きの決まり）をオンにする（`alter table ... enable row level security` を明示。自動の設定に頼らない）
- 表ごとの許可（GRANT）をマイグレーションに明示する。`authenticated` は必要な操作だけ（行の範囲は RLS で絞る）、`service_role` は守りのテストのため読み書きと削除、`anon`（ログインしていない人）には何も許可しない
- `service_role` の鍵と、表を流し込むための接続の文字（`SUPABASE_DB_URL`）は画面のコード（`src/`）で使わない。`VITE_` を付けた名前にしない（`VITE_` の付いた値は画面に埋め込まれ、だれでも見られるため）
- 表や権限を変えた計画では、報告書に「Security Advisor の確認が要る」と書く（Supabase の管理画面は本人のアカウントでしか開けない。本人が開いて写しを送り、Claude Code がレビューで確かめる）

### AI本人版レポート
- 本人版のAIへの入力に、部下メモ・責任者日報を含めない（コードで除外する）
- 守りのテストを変更・削除・スキップしない。通らないときはコードを直す。直せなければ止めて報告する

### 数値
- 数値計算はプログラムで行い、AIには計算済みの数値だけを渡す

### 変えやすくする（2026-10-10 本人の方針）
- 変わりやすいもの（商材、見込みのランク、部下メモのタグ、トークの分類の言葉、テーマの一覧、判定の線などの数字）は、コードに直接書かない。一覧（マスタ）の表か設定値として持ち、管理者が画面で足す・変えられるようにする

## 1. 目的（なぜやるか）
上席（リーダー・MGR・代表）が、指摘・指導・ほめた・面談などをテーマと種類で分けて記録し、次の確認日に「できたか（行動）・数字に出たか（結果）」を〇△×で残せるようにする。今のExcelでは確かめた結果が約3〜4割しか残っていない（設計書5章「部下メモの形（v14）」）。部下メモは本人には見せない。

## 2. やること
1. 部下メモの画面（`src/features/memo/`。左メニューの「部下メモ」＝リーダー・MGR・代表だけ。メンバーがアドレスで開いたときは「この画面は使えません」と出す）
   - 一番上に「確認待ち」：自分が書いて送ったメモのうち、次の確認日（`next_check_on`）が今日（日本時間）以前で、行動（`action_check`）がまだ空のもの。件数と一覧を出し、押すと行動・結果の〇△×と確かめた日（`checked_on`。初めは今日）を入れられる
   - 一覧：読めるメモ（自分が書いたものと、上席として見ている人についてのもの）を新しい日が上に並べる。日付・対象者（複数なら全員の名前）・テーマ・種類・気づいた内容と指導した内容の頭の部分・次の確認日・行動・結果・書いた人（リーダーは MGR・代表の名簿の行を読めないので、名前が読めないときは「ほかの上席」と出す）。対象者・テーマ・種類・期間で絞り込める。自分の書きかけは別にまとめて出す
   - 書く・直す：日付（初めは今日）、対象者（1人以上。下の「対象者の選び方」）、テーマ（一覧 `masters` の `memo_theme` で `is_active` が真のもの、並び順どおり）、種類（`memo_kind`。同じ）、気づいた内容（`noticed`）、指導した内容（`guidance`）、次の確認日（任意）。送るときは、テーマ・種類・対象者と、気づいた内容か指導した内容のどちらかが必須（データベースも止める）
   - 書きかけ：書くたびに自動で下書き保存し、「送る」を押すまで、ほかの上席には見えない（`submitted_at` が空。設計書9章「書く画面の決まり」。ロープレの記録の画面と同じやり方）
   - 送ったあとも、書いた人はいつでも直せる。消すときは見えなくするだけ（`hidden_at`）。対象者を外すときは `removed_at` を入れる（削除しない）。外した人を戻すときは、行を足し直さず `removed_at` を空に戻す（同じ人の行は1つまで）。送ったあとに直したメモは、最後に直した日時（`updated_at`）を「〇月〇日に直した」と出す（前の内容の控えは持たない。2026-11-05 本人の選択）
   - 書いた人のほかの上席が読むときは、見るだけ（直す欄を出さない）
   - 本人に見せないことを、書く画面に1行で出す（「このメモは対象の本人には見えません。AIの本人版にも渡しません」）
2. 対象者の選び方（2026-11-05 本人の選択：複数選べるのは同じチームの人だけ）
   - 選べる人：ログインしている人が上席として見ている人（リーダー＝今同じチームの人、MGR＝今担当しているチームの人、代表＝全員）。自分と、退職日を過ぎた人は除く。見る人の情報は①で作った `src/foundation/viewer.ts` の `canSuperviseMember` を使う
   - 1人目を選んだら、2人目からはその人と今同じチームの人だけを出す（チームがない人を選んだときは、ほかの人を足せない）。複数のチームに同じ指導をしたときは、チームごとに1つずつ書くことを画面に書く
   - リーダーとメンバーを一緒に対象にしたメモは、そのリーダーには見えなくなる（対象者に自分が入っているメモは読めない決まり）ことを、MGR・代表が選ぶときに知らせる
3. 計算の部品（`src/features/memo/` の中。画面やデータベースに頼らない関数）とテスト（`tests/memo/`）：確認待ちの選び出し（今日以前・行動が空・送ったもの・見えなくしていないもの）、対象者の選べる人と同じチームでの絞り込み、送る前の確かめ（必須の欄）

## 7. 守ること（毎回同じ。ひな形から変えない）

### データと秘密
- 社員の実名・人事評価を含むデータを作らない・読み込まない。開発用の見本は架空の名前と数字だけにし、fixtures/ に置く
- samples/ には本物の見本データ（実名あり）が入っている。開かない・読まない・検索しない・コピーしない
- APIキーは .env に置き、コードに書かない。.env の中身を表示・出力しない
- .gitignore を変更しない
- 雛形を作る道具（`npm create` など）で、既にあるファイル・フォルダ（ルートの `.gitignore`・README.md・CLAUDE.md・NOTES.md・docs/・tests/）を上書き・削除しない
- コミットの前に `git status` を見て、`.env` が入っていないことを確かめる

### 安全の決まり（2026-10-28 本人の選択）
- 表を足すときは、マイグレーションの中で RLS（行ごとの読み書きの決まり）をオンにする（`alter table ... enable row level security` を明示。自動の設定に頼らない）
- 表ごとの許可（GRANT）をマイグレーションに明示する。`authenticated` は必要な操作だけ（行の範囲は RLS で絞る）、`service_role` は守りのテストのため読み書きと削除、`anon`（ログインしていない人）には何も許可しない
- `service_role` の鍵と、表を流し込むための接続の文字（`SUPABASE_DB_URL`）は画面のコード（`src/`）で使わない。`VITE_` を付けた名前にしない（`VITE_` の付いた値は画面に埋め込まれ、だれでも見られるため）
- 表や権限を変えた計画では、報告書に「Security Advisor の確認が要る」と書く（Supabase の管理画面は本人のアカウントでしか開けない。本人が開いて写しを送り、Claude Code がレビューで確かめる）

### AI本人版レポート
- 本人版のAIへの入力に、部下メモ・責任者日報を含めない（コードで除外する）
- 守りのテストを変更・削除・スキップしない。通らないときはコードを直す。直せなければ止めて報告する

### 数値
- 数値計算はプログラムで行い、AIには計算済みの数値だけを渡す

### 変えやすくする（2026-10-10 本人の方針）
- 変わりやすいもの（商材、見込みのランク、部下メモのタグ、トークの分類の言葉、テーマの一覧、判定の線などの数字）は、コードに直接書かない。一覧（マスタ）の表か設定値として持ち、管理者が画面で足す・変えられるようにする
- 一覧や設定値を変えたら監査ログに残す。一覧の項目を消すときは論理削除にし、過去の記録の表示が崩れないようにする

### 業務ごとに分ける（2026-10-30 本人の方針）
- 業務（日報・ロープレ・KPI など）ごとに、表（マイグレーション）・画面・フォルダ（`src/features/〈業務〉/`）を分ける。ほかの業務のフォルダは触らない
- ほかの業務の表を書きかえない。複数の業務の表を読むのは、ダッシュボード・カルテ・AI分析だけ
- 名簿・ログイン・権限の土台は1つ。業務ごとに名簿や権限の仕組みを作らない

### 画面（Rush up 資料デザイン）
- 赤は1画面1〜2か所。未達は赤にしない（黒字＋▼＋「未達」）。増減には▲▼を必ず付ける
- 絵文字なし、影なし。画面の文言はすべて日本語

### Git
- 作業は作業用ブランチだけで行う。本線（main）に直接コミットしない
- コミットは区切りごとに行い、メッセージは日本語で「何をしたか」を書く
- 本線への取り込み（merge）、push、`--force`、履歴の書き換え（rebase・reset --hard）はしない

## 1. 目的（なぜやるか）
リーダー・MGR・代表が、部下1人ひとりの「数字」と「指導の記録」を1画面（メンバーカルテ）で見られるようにし、ログインしたらまず「今日やること」（ホーム）が開くようにする。節目①で、リーダー層に数日触ってもらう形にする（設計書10章「カルテは KPI → 約束 → 推移 → 時間帯 → 育成 → 記録の順」）。

## 2. やること
先に計算の部品とテスト（1）を作って通してから、画面（2・3）を作る。

1. 計算の部品（`src/features/karte/shared/` と `src/features/home/shared/`。画面やデータベースに頼らない関数にする）とテスト（`tests/karte/`・`tests/home/`）
   - **選べる人**：見る人ごとに、カルテで選べる人の一覧を、名簿・所属の履歴・MGR の担当から計算する（データベースの読める範囲に頼らない。管理者の権限がある人は名簿を全員読めるため）。リーダー＝今の自分のチームの人、MGR＝今担当しているチームの人、代表＝全員。退職した人（退職日が今日より前）は、所属の履歴のうち開始日がいちばん新しい行のチームを「最後のチーム」とし、そのチームの今のリーダー・担当MGRと代表が選べる（2026-11-07 本人の選択）。自分自身は選べない。`src/foundation/viewer.ts` の `canSuperviseMember` は退職した人に使えない（チームが空になる）ので、この判定は karte の中で作る
   - **基準の日**：その人のその月の、承認済みの日々のKPIがある最後の日（取り込みは業後なので、今日の数字はまだないことが多い。KPI の月のペースも取り込んだ日で判定している）。その月の KPI がまだないときは「今月の数字はまだありません」
   - **KPI の集計**：期間ごとの、総・実・再・オ・見・アの実績の合計と率（実率＝実÷総、再率＝再÷総、オ率＝オ÷総、見率＝見÷総、ア/オ＝ア÷オ。分母が0のときは「－」）。期間は「今日」＝基準の日の1日、「今週」＝基準の日を含む週（月曜はじまり）の初めから基準の日まで、「今月」＝月の初めから基準の日まで
   - **目標とあるべき**：その月の目標（月の途中で直した目標は、基準の日に効いていた値。`src/features/kpi/shared/` の `resolveTargetValuesAtDate` と `calculateKpiTargets` を使う）。「今日」は日次の目標、「今週」は日次の目標 × 今週の初めから基準の日までの営業日の数、「今月」は月の目標と、あるべき（①で足した `src/features/kpi/shared/` のあるべきの関数。基準の日まで）。あるべき比（実績 ÷ あるべき。今日・今週は実績 ÷ その期間の目標）と▲▼。ア/オは率のまま目標と比べる。営業日は `kpi_holidays`・`kpi_workdays` で数える
   - **コール時間と未達の時間数**（今の KPI ブックの式。NOTES の見本データ1）：9〜12時台と14〜17時台の8つの時間帯だけを数える（13時台は昼休みとして除く）。コール時間 ＝ 総が設定値 `karte_call_hour_threshold`（初めは17）を超えた時間帯の数。未達の時間数は**項目ごと**（総・実・再・オ・見・ア）に、その時間帯の実績が「1時間あたりの目標」を下回った時間帯の数。1時間あたりの目標は、総＝ターム、実・再・オ・見＝ターム × それぞれの率の目標、ア＝ターム × （月次のアの目標 ÷ 月次の総の目標）（今の KPI ブックと同じ考え方。途中で丸めない）。日ごとに数え、期間の合計も出す。営業日でない日（入れていない土曜・日曜・休みの日）は数えない
   - **時間帯別**：時間帯（14区分）ごとの総・実率・ア（期間の合計）。その人の月の実率の目標を下回る時間帯を「弱い時間帯」とする（総が0の時間帯は除く）
   - **チームの中の比べ**：選んだ人の今のチームの、今いる人（退職した人は除く）の中での、今月のアポ数の順位と、アポの達成率（アポ ÷ 基準の日までのあるべきアポ）の順位。目標がない人は達成率の順位から外す。関わった受注と粗利の達成率の順位は「一般日報の区切りで出ます」。退職した人を選んだときは、順位を出さない
   - **推移**：日ごとのアと総（2か月分）と、指導した日（その人を対象にした部下メモの日付と、その人のロープレの日付）
   - **タイムライン**：ロープレの記録・研修の記録・部下メモ（上席だけ）を、日付の新しい順に混ぜて並べる。種類で絞り込める。過去の記録（`is_legacy` が真）は「過去の記録」の印をつけ、元の行（`legacy_source`）の中身を見られるようにする。テーマなどが空の過去の記録が来ても崩れないようにする（④で本物を入れるため）
   - **ホームの件数**（下の3。今の画面と数え方をそろえる）

## 7. 守ること（毎回同じ。ひな形から変えない）

### データと秘密
- 社員の実名・人事評価を含むデータを作らない・読み込まない。開発用の見本は架空の名前と数字だけにし、fixtures/ に置く
- samples/ には本物の見本データ（実名あり）が入っている。開かない・読まない・検索しない・コピーしない
- APIキーは .env に置き、コードに書かない。.env の中身を表示・出力しない
- .gitignore を変更しない
- 雛形を作る道具（`npm create` など）で、既にあるファイル・フォルダ（ルートの `.gitignore`・README.md・CLAUDE.md・NOTES.md・docs/・tests/）を上書き・削除しない
- コミットの前に `git status` を見て、`.env` が入っていないことを確かめる

### 安全の決まり（2026-10-28 本人の選択）
- 表を足すときは、マイグレーションの中で RLS（行ごとの読み書きの決まり）をオンにする（`alter table ... enable row level security` を明示。自動の設定に頼らない）
- 表ごとの許可（GRANT）をマイグレーションに明示する。`authenticated` は必要な操作だけ（行の範囲は RLS で絞る）、`service_role` は守りのテストのため読み書きと削除、`anon`（ログインしていない人）には何も許可しない
- `service_role` の鍵と、表を流し込むための接続の文字（`SUPABASE_DB_URL`）は画面のコード（`src/`）で使わない。`VITE_` を付けた名前にしない（`VITE_` の付いた値は画面に埋め込まれ、だれでも見られるため）
- 表や権限を変えた計画では、報告書に「Security Advisor の確認が要る」と書く（Supabase の管理画面は本人のアカウントでしか開けない。本人が開いて写しを送り、Claude Code がレビューで確かめる）

### AI本人版レポート
- 本人版のAIへの入力に、部下メモ・責任者日報を含めない（コードで除外する）
- 守りのテストを変更・削除・スキップしない。通らないときはコードを直す。直せなければ止めて報告する

### 数値
- 数値計算はプログラムで行い、AIには計算済みの数値だけを渡す

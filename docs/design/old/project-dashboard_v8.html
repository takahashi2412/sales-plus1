PART 1

全体：何が、どこから、どこへ流れるか

1システム構成：電話システムのデータと人の記録が、1つのアプリに集まる

KPIは電話システム（CTI）から取り込み、ほかの5業務は人が入力します。計算はプログラム、解釈はAIが行います。

図の見方
  • 左が「入るもの」、中央の濃紺の枠がアプリの中、右が「使う人」
  • 点線の箱は、アプリの外にある既存の仕組み
  • 矢印はデータが流れる向き
ポイント
  • データベースが中心。すべての記録がここに集まる
  • アラートはAIを使わず、閾値で速く確実に判定する
  • 認証（ログイン）は会社のMicrosoft 365アカウントで確定（Microsoft Entra ID）。DB・ホスティング・AIの連携先は未決（技術構成で決める）
  • 使う人は合計約30〜60人。拠点が複数あり、スマホは社外から使う可能性がある（確定）

2データの流れ：数字が電話システムから画面に届くまで

1件の通話記録が、チェック・保存・集計を経て、アラート・AIレポート・カルテの数字になるまでの道筋です。

図の見方（番号の順に進む）
  1. 電話システムの管理画面から、通話の記録をCSVで出す
  2. 形式が正しいか、同じデータの二重取り込みがないか、名前がIDの対応表にあるかを確かめ、管理者が承認する（自動化後は自動で承認）
  3. 承認した数字を表（テーブル）に保存する
  4. 率・前週比・チーム平均との差、目標との差を計算する
  5. 本人が設定したKPIの目標に届かなければ、承認の直後にリーダーの画面へ知らせる
  6. AIに渡すデータを、本人版・指導版で分けて用意する
  7. AIが原因の仮説と提案を文章にする
  8. AIの文章を保存し、⑨画面に表示する
ポイント
  • AIに届くのは④で計算済みの数字だけ。AIに計算させないので、数字の誤りが起きない
  • ②のチェックが甘いと、二重計上や別人のデータが混ざる。取り込みはいちばん慎重に作る部分。チェックの中身は見本のCSVで確定（セクション3-2）
  • 日報・メモなど人の入力は、②を通らず直接③に入る
  • 一般日報は、その日のKPIを見て書くので、業後までに①〜④が終わっている必要がある。採用・訪問件・受注はCSVにないので、日報で本人が入力する

3KPIの取り込み：今は手作業、いずれブラウザ自動操作で

電話システムにはAPIがないため、人がする操作をブラウザ自動操作に置き換えます。ログインはIDとパスワードだけなので、自動化しやすい形です。

図の見方
  • 上の段が今の手作業、下の段がいずれの自動化。やっている中身は同じ
  • 濃紺の箱は、プログラムが代わりに行う部分
  • 点線の矢印は、失敗したときの逃げ道
ポイント
  • 取り込みは今もいずれも終業後に1回（まとまり4で確定）。アラートは承認の直後に出る。回数は設定で増やせる作りにする
  • CSVはチームごとに分かれる（ファイル名の「zoom(WEB)」はチーム・部署の名前）。1日に2〜3ファイルを取り込む
  • 電話システムの画面が変わると止まるため、失敗の通知は必須。止まっている間は手作業に戻す
  • 自動化に取りかかる前に、電話システムの利用規約で自動操作が禁止されていないか確かめる
  • 自動化には「ブラウザを動かせる場所」が必要。これが技術構成を選ぶ条件の1つになる
  • ログイン情報は.envに置き、.gitignoreでGitHubに上がらないようにする

3-2KPIの項目：9つの段階と、それぞれの出どころ（見本データで確定）

今のKPIブックと電話システムのCSVを見て確定しました。KPIは9つの段階のファネルです。前の6つは電話システムのCSVから時間帯ごとに取り込み、後ろの3つは日報で本人が入力します。

率の計算のしかた

率計算見ている力
実率・再率・オ率・見率・ア率それぞれ ÷ 総かけた数のうち、どこまで進んだか（リストと時間帯の良し悪し）
ア/オア ÷ オ決裁者に会えたときに、アポにつなげる力（トーク）
採用率採用 ÷ アアポが日程確定まで進んだ割合（アポの質）
訪問率訪問件 ÷ アアポが実際の訪問になった割合
受注率受注 ÷ 訪問件訪問が契約になった割合

「再」は、つながらなかった相手も含むため、「実」より多くなることがあります。そのため、実〜アの率は、前の段階ではなく「総」を分母にしています。

月初の目標の立て方：2つの方向から日次KPIを決める（数字は架空の例）

図の見方
  • 上の図：濃紺の6つはCSVから自動、白の3つは日報で入力
  • 時間帯の帯：濃紺が「未達の時間数」を数える8時間
  • 下の図：上の段は「いくら稼ぐか」から必要なアポ数を、下の段は「何時間かけるか」から必要なコール数を出す。総の目標に転換率の目標を掛けると、実・再・オ・見の日次KPIになる
ポイント
  • 今はメンバーが時間帯ごとに手で記入している。アプリではCSVから取り込むので、この記入がなくなる
  • 本人が入力するのは、月初の目標（目標粗利・単価・稼働日・完了率・コール時間・転換率・ターム）と、毎日の採用・訪問件・受注だけ（今のExcelの黄色いセル）
  • コール時間と未達の時間数は、時間帯ごとの「総」から自動で計算する（手で入力しない）
  • アラートの基準は、ここで本人が立てた日次KPI・月次KPI（まとまり4）。KGIから逆算した数字が、そのまま物差しになる
  • CSVの文字コードはShift_JIS。人は名前で並んでいるので、「電話システムの名前 → メンバーID」の対応表で結ぶ
PART 2

データのつながり：記録どうしが、どう結びつくか

4つながりの全体：すべての記録が「メンバー」を中心に結びつく

記録は「メンバーID × 日付 × 記入者」で紐づきます。だからカルテで1人分を1画面に並べられます。

図の見方
  • 中央の「メンバー」から8本の線が出ている。線は「同じメンバーIDを持つ」という意味
  • 橙の箱（部下メモ）は、本人に見せない記録
ポイント
  • どの記録にも必ず「誰の」「いつの」「誰が書いた」を持たせる。1つでも欠けるとカルテに並べられない
  • 今のExcelは業務ごとに別のファイルなので、この「共通の鍵」がない。統合の価値はここにある

5データの設計図：20の表と、それぞれの項目（KPIまわりは確定、ほかは案）

データベースの中の表（テーブル）と、主な項目です。このような図をER図と呼びます。v8で、KPIブックと電話システムのCSV（見本データ）に合わせて、日々のKPI・月の目標・一般日報・アラートの項目を確定し、取り込みまわりの4表（取り込みの記録・狙うリスト・名前の対応・チーム名の対応）を加えました。

濃紺の文字＝ほかの表とつなぐ鍵（ID）や、必ず入れる項目 実線＝member_id でつながる（1対多） 点線＝言及メンバーで複数人につながる
図の見方
  • 1つの箱が1つの表。濃紺の帯が表の名前、その下が項目
  • 中央の members が名簿。ほかの表は member_id で名簿とつながる
  • 1人のメンバーに、日報やKPIの記録がたくさんぶら下がる（1対多）
  • AIの提案が「採用」されると、週間教育の記録になる
  • 名簿の上の「所属の履歴」は、いつからどのチーム・拠点にいたかの記録（v5で追加）
ポイント
  • 表の名前は英語（プログラムで扱いやすいため）、画面には日本語で表示する
  • 項目は案。見本データ（今のExcel）を見て、列を確定させる
  • ロープレは「内容・時間」が本人の補足。点数をつけるかは未決（下の「必ず入れる設計」を参照）
  • 異動しても、過去の数字は当時のチーム・拠点で集計する。だから過去のチーム平均が変わらず、効果の確かめの比較が狂わない

後から足すのが難しい「必ず入れる設計」（引き継ぎ資料より）

狙うKPI週間教育に必須。取り組みの効果をプログラムで判定するため
ロープレの固定項目自由記述だけにしない。項目ごとの点数があると弱点を比べられる（要確認）
部下メモの種別タグ指示・指摘・面談などで分け、集計できるようにする
言及メンバー責任者日報をチーム単位から個人カルテにも出すため
AI提案の採否と理由採用率を集計し、提案の精度を上げるため

6責任者日報とカルテ：チームの記録を、言及した人のカルテに自動で出す

責任者日報はチーム単位の記録です。「言及メンバー」の欄で名前を選ぶと、その人のカルテのタイムラインにも表示されます。

図の見方
  • 左が1件の責任者日報。下の濃紺のタグが「言及メンバー」
  • タグを付けた人のカルテにだけ、矢印が伸びる
ポイント
  • リーダーは日報を1回書くだけで、関係する部下全員のカルテに記録が残る
  • タグがないと、チームの記録は個人のカルテに出ない。入力画面でタグを選びやすくすることが大事
  • ここで表示されるのは、リーダー・MGR・代表が見るカルテ。メンバー本人の制限版のカルテには、責任者日報は出ない（確定）

7AIに渡すデータ：本人版には、部下メモと責任者日報を渡さない

AIへの指示で「触れないで」と頼むだけでは漏れを防ぎきれません。そのため、渡す前のデータの段階でプログラムが取り除きます。

図の見方
  • 左が材料のデータ、中央がAIに渡す前の選別、右ができあがるレポート
  • 濃紺の矢印が本人版（4本）、灰色の線が指導版に入るデータ
  • ×印は、本人版に入れずに止めるデータ
ポイント
  • 本人版の材料は、KPI・自分の日報・ロープレ結果・週間教育の4つ。週間教育は問題・原因も含めてすべて渡す（まとまり3で確定）。本人はもともと自分の週間教育を見られるので、見える情報は増えない
  • この選別は「守りのテスト」で毎回自動で確かめる。作る係（Antigravity）はこのテストを変更できない決まり
  • 本人版は、責める言い方をせず「次の一手」を1つに絞って書く。週間教育の「原因」も、次の一手として言い換えるようAIに指示する
  • 本人版は担当リーダー・MGRも全体を見る（確定）。そのため、本人の画面にその旨を表示する

8効果の確かめ：週間教育の「狙うKPI」と、KPIの記録をつなぐ

取り組みが効いたかを、本人の数字だけでなく、同じ期間のチーム平均と比べて判定します。チーム全体が上がっただけなら、取り組みの効果とは言えないためです。数字は架空の例です。

判定のルール（まとまり3で確定）

判定条件この例では
判断できない期間中の件数が下限に届かない。偶然の動きと区別できないため、判定を出さない15時台の架電が下限未満なら、ここで止まる
効果あり本人の上がり幅 − チーム平均の上がり幅 が、その指標の基準以上8.0pt − 1.0pt ＝ 7.0pt。接続率の基準が3ptなら「効果あり」
変化なし差が基準に届かない（上下どちらにも）差が2ptなら「変化なし」
逆効果の疑い差が、マイナスの基準を下回る（本人だけが下がった）差が −4ptなら「逆効果の疑い」

基準（例の3pt）と件数の下限は指標ごとに変え、見本データでふだんの動き方を見てから、まとまり5で初期値を決めます。運用中は管理者が設定画面で変えられ、変更は監査ログに残ります。

図の見方
  • 左が週間教育の記録。ハイライトの「狙うKPI」が、右のグラフで見る数字
  • グラフの赤は本人、灰色はチーム平均。薄い棒が取り組みの前、濃い棒が後
  • 増えた幅はptで表す
  • 「判定のルール」の表は、プログラムが出す4つの判定と、その条件
ポイント
  • 「狙うKPI」が空欄だと、この判定がプログラムでできない。だから必須の欄にする
  • 判定はプログラムが行い、結果を翌週のAIの提案に反映する（AIサイクルの⑤）。判定結果はAIの提案の表に記録する
  • まず「判断できない」を確かめてから判定する。件数が少ないまま「効果あり」と出すと、偶然を効果と取り違える
  • 基準の値は設定値として持ち、コードに直接書かない

データと仕組み

KPI重要業績評価指標
目標に向かって進んでいるかを測るために、毎日追いかける数字。
総・実・再・オ・見・ア・採用・訪問件・受注の9段階と、その率。前の6つは時間帯ごとに記録する（セクション3-2）。
ファネル漏斗（じょうご）
段階を進むごとに数が絞り込まれていく流れ。上が広く下が細い、じょうごの形にたとえた言い方。
総 → 実 → 再 → オ → 見 → ア → 採用 → 訪問件 → 受注 の9段階。
転換率
ある段階の数が、次の段階（または基準の数）に変わった割合。
実率＝実÷総、ア/オ＝ア÷オ、採用率＝採用÷ア、受注率＝受注÷訪問件。月初に本人が目標を立てる。
ターム
今のKPIブックで使っている、1時間あたりのコール数の目標。
見本では20〜30件。「1日のコール時間 × ターム」で日次の総コール目標になる。タームに届かない時間の数を「未達の時間数」として自動で数える。
KGI重要目標達成指標
最終的に達成したい結果の目標。KPIはそこに至るまでの途中の目標。
月の受注件数。目標粗利（単位P）÷単価÷完了率で出し、そこから採用・アポの必要数を逆算する。
Shift_JIS文字コード
日本語の文字をコンピューターの数字に置き換える決まりの1つ。Windowsの古いソフトでよく使われる。今の主流はUTF-8で、決まりが違うと文字化けする。
電話システムのCSVはShift_JIS。取り込むときにアプリの文字コードに変換する。
承認
内容を確かめて「これで正しい」と認め、次に進めること。
取り込んだKPIは、取り込んだ管理者が件数やエラーを確かめて承認してから画面に出る。自動化後は、チェックに通れば自動で承認。
CTIComputer Telephony Integration
電話とコンピューターをつなぐ仕組み。架電や通話の記録が自動でたまる。
今使っている電話システム。KPIの出どころ。
CSVComma-Separated Values
値をカンマで区切って並べた、文字だけの表のファイル。Excelで開ける。
電話システムの管理画面から出力する、時間帯別の通話記録のファイル。チームごと・1日分ずつ出す。
APIApplication Programming Interface
システム同士がデータをやり取りするための窓口。あると、ほかのシステムから直接データを取れる。
電話システムにはAPIがない。だからブラウザ自動操作を使う。
ブラウザ自動操作RPA・ヘッドレスブラウザ
人がブラウザで行うクリックや入力を、プログラムが代わりに行うこと。画面を表示せずに動かすブラウザを「ヘッドレスブラウザ」と呼ぶ。
定時に管理画面へログインし、CSVを出してアプリに取り込む。
データベースDB
データを整理して保存し、条件ですばやく探したり集計したりできる仕組み。Excelのブックに近いが、大量のデータや同時の書き込みに強い。
6業務とメンバーの記録をすべてここに保存する。種類は技術構成で決める。
テーブル表
データベースの中の1つの表。Excelのシートに近い。1行が1件の記録。
members（メンバー）、kpi_entries（日々のKPI）など20の表（セクション5）。
項目列・カラム
表の縦の列。どんな情報を記録するかを決めるもの。
日付、時間帯、架電数、狙うKPI など。見本データを見て確定する。
ID識別番号
1件ずつを区別するための番号。名前が同じ人がいても、IDで区別できる。表の中で必ず1つに決まるIDを「主キー」と呼ぶ。
member_id。すべての記録がこれで名簿とつながる。
所属の履歴
誰が、いつから、どのチーム・拠点に所属していたかの記録。今の所属だけでなく、過去の所属も残す。
異動前の数字を当時のチーム・拠点で集計するために使う。過去のチーム平均が変わらない。
1対多
1件の記録に対して、関係する記録が何件もある関係。
1人のメンバーに対して、日報・KPI・メモがたくさんある。
ER図テーブル関連図

集計
細かい記録を、合計・平均・割合などにまとめること。

閾値しきい値
判定の基準になる値。これを超えたら（下回ったら）反応する、という境目。
アラートでは、本人が月初に立てた日次KPI・月次KPIが閾値になる。効果の判定の基準値や件数の下限も閾値の一種。

AI生成AI
文章を読んで考え、文章で答えを出すプログラム。計算や数字の正確さは苦手なので、計算はプログラムにまかせる。

push／pull
push は手元の記録をGitHubへ送ること。pull はGitHubから最新を取ってくること。
pushは毎回確認を取ってから。作業を始める前に必ず pull する。
.env
パスワードやAPIキーなどの秘密の値を置くファイル。コードに直接書かないために使う。
電話システムのログイン情報やAIのキーを置く。Gitには入れない。
.gitignore
Gitに入れない（GitHubに上げない）ファイルの一覧。
.env、Excel・CSV、録音、PDFなどを止めている。

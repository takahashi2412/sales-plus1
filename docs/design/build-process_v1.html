PART 1

全体：何を、どの順番で、だれが作るか

1作る順番：土台から自動化まで、9つの区切りで1つずつ作る

変更 2026-11-04：管理の画面のうち「名簿・所属・MGRの担当」と「権限」は、カルテ第1版で作ります。区切りは番号ではなく、中身の名前で呼びます（区切りの名前は、同じ時期に作るもののまとまりで、画面のまとまりではありません。例：「KPI・部下メモ」は、KPI の画面と部下メモの画面を同じ時期に作るという意味で、サイトでは別々の画面です）。表と守りのテストは1本で作り、画面だけを2本の並列で作ります。橙の3つは、数日触って確かめる節目です。

図の見方
  • 左上から右へ、下の段に折り返して、9つの区切りを順に作る
  • 箱の下の小さい字は、その区切りを何本で作るか（「表1本 → 画面2本」は、表とテストを1本で作ってから、画面を2本の並列で作る）
ポイント
  • 土台（ログイン・名簿・権限）で、いちばん技術の不安が大きい所を先に小さく確かめる
  • 集める画面（カルテ・ホーム・ダッシュボード）は、カルテ第1版と「責任者日報・集める画面」の2回だけ作る。ほかの区切りでは触らないので、並列でぶつからない
  • 詳しい中身は設計書 v28 の13章

23者の役割：決めるのはご自身、考えて確かめるのは Claude Code、作るのは Antigravity

だれすることしないこと
ご自身選択式の質問で決める。作業用フォルダを Antigravity で開いて計画を渡す。画面で確かめて OK を出す。GitHub に送る（push）。管理画面の設定（Supabase・Microsoft 365）コードを書く・レビューする
Claude Code設計・案を出す・記録する。計画ファイルを作る。作業用フォルダを用意して片づける。差分をレビューする。本線（main）に取り込む。守りのテストを書くアプリのコードを書く。ご自身の OK の前に本線へ入れる
Antigravity計画ファイルどおりにアプリを作る。テストを通す。報告書を書く。作業用ブランチにコミットする本線への取り込み・push。守りのテストを変える。計画にないことを決める
別のエージェント（別の目）区切りごとに、決定の一覧と資料だけを読んで、反映の漏れを探す（別の目の点検）ファイルを変える。実名の入った資料や .env を開く
図の見方
  • 1行が1人（1つの役）。右の列は、その役がしてはいけないこと
ポイント
  • 作る係（Antigravity）と確かめる係（Claude Code）を分けて、作る係の誤りを別の目で見つける
  • Antigravity は CLAUDE.md を読まないので、守らせたい決まりは毎回計画ファイルに書く
PART 2

1つの計画を作る：決めてから片づけるまで

312の手順：作るのは⑦だけ。その前後に、漏れと誤りを止める所を4つ置く

縦が手順の順番、横がだれの番かを表すレーン図です。⑦で Antigravity が作っている間、Claude Code は同時に次の計画を作ります（点線の箱）。

図の見方
  • 上から①〜⑫の順に、矢印をたどる。箱がある列が、その手順をする人
  • ①は、ご自身が選び、Claude Code が影響表から直す場所をたどって記録する（7章）
  • ⑤は、作業用フォルダ（ワークツリー）と作業用ブランチを作り、.env を写すこと（4章）
ポイント
  • 誤りを止める所は4つ：③別の目の点検、⑧レビュー（守りのテストが変わっていないかも見る）、⑨ご自身の確認、Antigravity のテスト
  • ⑨は、報告書に書かせた「本人が画面で確かめる手順（3〜5行）」で、5〜10分で済むようにする
  • 1つ作るごとに、かかった日数・差し戻しの回数・レビューの指摘の数を測る

42つのフォルダ：元のフォルダで考え、作業用フォルダで作る

作業用フォルダは、同じアプリのファイル一式をもう1部開いたものです。2026-10-30 にこのPCで、作る・確かめる・片づけるを試して確かめました。

図の見方
  • 左が元のフォルダ、右が作業用フォルダ。矢印は、⑤で .env を写すこと（写すのはご自身。2026-11-04 から。Claude Code の実行環境の決まりで、Claude Code からは写せないため）と、⑧で作業用フォルダの記録（コミット）を元のフォルダから見ること
  • 左の3つ目の箱（samples/）は、元のフォルダにだけある、実名の入った見本
ポイント
  • フォルダが違うので、Claude Code と Antigravity が同時に作業してもぶつからない
  • samples/ は作業用フォルダにできないので、Antigravity が誤って実名を読むことがない
  • 作業用フォルダでは本線に切り替えられない。だから計画ファイルの最後は「作業用ブランチのまま終える」にしてある
  • 置き場所はいつも C:\Workspace\apps\sales-plus1-worktrees\〈計画の名前〉\。用意と片づけは Claude Code
PART 3

並列で作る：2本まで、表は先に1本で

5並列の流れ：共通の部分を1本で作ってから、画面を2本同時に作る（ロープレの例）

ロープレの区切りを例にした流れです。左から右へ時間が進みます。作るのは同時でも、レビューとご自身の確認は1本ずつです。

図の見方
  • 横の帯が人、箱がその人の作業。箱の左右の位置が時間
  • 薄い青の2本（記録の画面・トーク一覧）が並列の部分。それぞれ別の作業用フォルダ・別のブランチで作る
ポイント
  • 表の定義（マイグレーション）と共通の部品は、2本が同時に触るとぶつかるので、先に1本で作って本線に入れる
  • 並列で速くなるのは「作る」だけ。レビューと確認は1本ずつなので、本数はご自身が確かめられる量（2本）に合わせた
  • 開発用の Supabase は1つを共有するので、表を変える作業は1本だけ

6並列の決まり：同時に進めてよいのは、3つの条件がすべてそろうときだけ

決まり中身
作業の場所Antigravity は、並列でないときもいつも別の作業用フォルダで作る。並列の2本は、それぞれ別の作業用フォルダ・別のブランチ。「1つの計画ファイル＝1つのブランチ＝1つの報告書」
本数最大2本。2本とも本線に取り込むまで、次の並列は始めない
並列にしないもの表の定義（マイグレーション）・架空データ・守りのテスト・共通の部品。その区切りの先頭で1本で作る
同時に進めてよい条件①ほかの作業の結果が要らない ②同じファイルを触らない ③1つの変更として一緒に出さない、の3つがすべて当てはまるとき
触ってよい範囲計画ファイルに「触ってよいファイル・フォルダ」と「触ってはいけないもの」を書く。範囲の外が要るときは止めて質問させる
業務ごとの分け方業務ごとに表・画面・フォルダ（src/features/〈業務〉/）を分け、ほかの業務の表は書きかえない。だから2本が別の業務の画面なら、ぶつかりにくい
見た目のそろえ方最初の1画面（または共通の部品）でデザインのお手本を固めてから、並列の画面に参照させる
図の見方
  • 1行が1つの決まり。CLAUDE.md の「開発体制」と、計画ファイルのひな形にも同じことを書いている
ポイント
  • Antigravity との壁打ち（2026-10-27）で、両方の AI がほぼ同じ結論を出した決まり
  • 並列に入る前の「ワークツリーの試し」は 2026-10-30 に済んだ
PART 4

漏れを防ぐ：決めたことを、全部の資料に確実に届ける

7決め方・直し方：一覧を先に作り、機械で毎回、別の目で区切りごとに確かめる

2026-10-30 に、Claude Code 自身の点検を2回しても反映の漏れが残り、別のエージェントの点検で14件が見つかりました。その反省から決めた5つの手順です。

図の見方
  • 左から順に、1つの決定を資料に反映する流れ。濃紺の4だけが区切りごと、ほかは決定のたび
ポイント
  • 漏れの多くは、直す場所の一覧を最初に作らなかったことから来ていた。だから2で影響表から一覧を作る
  • 3では、古い言葉・版の番号・リンク切れ・用語集・図の文字のはみ出し・横はみ出し・文字化けを確かめる。\ を含む書き込みは、書いたあとに読み返す（実際に2回、文字化けを見つけた）
  • 4（別の目）は1回に約4分・約20万トークンかかるので、毎回ではなく区切りごと
用語集

この資料で使った言葉

本文の点線の下線から移動してきた場合、その言葉の枠が濃紺で囲まれます。「この案件での例」は、SALES +1 での具体例です。

作る場所と道具

ワークツリー作業用フォルダ
同じリポジトリ（Git で管理しているフォルダ）を、別のフォルダにもう1つ開いたもの。フォルダごとに別のブランチで作業できるので、同時に作業しても上書きし合わない。
C:\Workspace\apps\sales-plus1-worktrees\〈計画の名前〉\。Antigravity はいつもここで作る。用意と片づけは Claude Code。
ブランチ
本線から分けた作業用の枝。枝の上で作業すれば、OK が出るまで本線を変えずにすむ。
作業用ブランチは task/〈計画の名前〉（例：task/foundation）。作業用フォルダと一緒に作る。
本線main
正式な最新版を置くブランチ。
元のフォルダ（apps\sales-plus1）が使っている。ご自身の OK のあとに、Claude Code が取り込む。
差分
2つの版のあいだで、どこが変わったか。
⑧のレビューで、本線と作業用ブランチの差分を、元のフォルダから見る。
レビュー
できあがった変更を、取り込む前に別の目で確かめること。
Claude Code が、計画ファイルと「守ること」に沿っているか、守りのテストが変わっていないかを確かめる。
push
手元の Git の記録を GitHub へ送ること。
ご自身のターミナルで行う（④と⑪）。送る前に、別の目の点検をする。
.env
パスワードや API キーなどの秘密の値を置くファイル。Git に入れない。
Supabase の URL と鍵を入れる。作業用フォルダには、ご自身が中身を開かずに写す（Claude Code が渡す Copy-Item の1行を、ご自身のターミナルで実行する）。
マイグレーション
データベースの表の作り方や変え方を書いた SQL のファイル。順に流し込むと、同じ表がいつでも作り直せる。
supabase/migrations/ に置く。2本が同時に変えるとぶつかるので、並列にしない。
守りのテスト
絶対に崩してはいけない決まりを、プログラムが毎回自動で確かめるテスト。作る係は変更・削除・スキップしてはいけない。
tests/guard/ に置く。今は権限のテスト（役割ごとに読める範囲・書ける範囲）。担当は Claude Code。
共通の部品
どの画面でも使う部品。左メニュー・画面の枠・共通の型・パッケージ（入れた道具の一覧）など。
ロープレの区切りの先頭で1本で作り、本線に入れてから、画面を2本の並列で作る。

進め方

計画ファイル
作る係に渡す作業の指示書。目的、やること、触ってよい範囲、完了の条件、守ることを書く。
docs/tasks/plan_〈内容〉_v1.md。ひな形は plan_template.md。土台は plan_foundation_v1.md。
報告書
作る係が作業のあとに書く、やったこと・テストの結果・質問のまとめ。
docs/reports/report_〈内容〉_v1.md。「本人が画面で確かめる手順（3〜5行）」も書かせる。
区切り
作る順番の1つのまとまり。番号ではなく中身の名前で呼ぶ。同じ時期に作るもののまとまりで、画面のまとまりではない（「KPI・部下メモ」の KPI と部下メモは、サイトでは別々の画面）。
土台・ロープレ・KPI・部下メモ・カルテ第1版・一般日報・週間教育・責任者日報・集める画面・AI・自動化の9つ。
並列
複数の作業を同時に進めること。
Antigravity のエージェントを2本まで同時に動かし、別々の画面を作らせる。
節目
次へ進む前に、ご自身や現場の人が数日触って確かめる時点。
①カルテ第1版（リーダー層に数日）②一般日報（スマホで1日分）③AI（1週間の輪を通して）。
別の目の点検
決めたことを反映し終えたあと、別のエージェントに決定の一覧と資料だけを渡し、独立に漏れを探させること。
区切りごと（計画ファイルを渡す前と、GitHub に送る前）。読むだけで、実名の資料と .env は開かせない。
影響表
ある決定を変えたときに、どのファイルのどこを直すかの一覧。
NOTES.md の「決定を変えたときに直すファイル」。この資料も、作業の場所・作る順番・決め方の行に入っている。

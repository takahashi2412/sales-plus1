## 論点1：この順番でよいか
- 結論：
  - 基本の8周の流れ（特に **周1「E 土台」→ 周2「A ロープレ」→ 周3「KPI と 部下メモ」** の順番）に賛成です。
  - そのうえで、本人に早く価値を見せ、後の周の手戻りを減らすために、次の**3点だけ順番の入れ替え・追加**を提案します。
    1. **周3の直後に「カルテとホームの第1版（KPI＋ロープレ＋部下メモ）」を1本入れる**（論点2と連動）
    2. **「研修の記録（`seminars`）」は周4（一般日報）より前に済ませる**（周2のロープレ、または周3の部下メモに含める）
    3. **「過去の記録の取り込み」を周8（最後）から前倒しし、カルテやAI（周7）を試す前に入れる**

- 理由・入れ替えの案：
  1. **周1〜周3の順番が良い理由（もとの第1段階と完全に一致する）**
     - 設計書13章の第1段階は「名簿・部下メモ・ロープレ（リーダー層から）、KPI は CSV を手で取り込み」です。周1〜周3が終われば、メンバー20〜50人の毎日の動きを変えずに、リーダー層（2〜3人）と管理者だけで使い始める材料がすべて揃います。
  2. **入れ替え案①：周3の直後に「カルテ第1版」を出して、一番の価値を早く見せる**
     - このアプリの中心価値は「1人を開けば、数字（KPI）と指導の記録（ロープレ・部下メモ）が1画面でつながり、指導した日の前後で数字が動いたか見えること」です。
     - 周3で KPI・ロープレ・部下メモの3つが揃うため、周6まで待たなくても、この時点でカルテの主要部分（基本情報・KPI9段階・推移と指導日の縦線・時間帯別・ロープレと部下メモのタイムライン）が作れます。ここで一度カルテを見せることで、本人とリーダーが早い段階で手応えを確かめられます。
  3. **入れ替え案②：「研修の記録（`seminars`）」を周4より前に置く**
     - 周4の「一般日報」には「今日のロープレ・研修が自動で並び、研修があった日は学んだことを書く」仕組みがあります。そのため、研修の記録（`seminars, seminar_members`）は周5ではなく、周2（ロープレの仲間として）または周3のうちに作っておくと、周4で手戻りが起きません。
  4. **入れ替え案③：「過去の記録の取り込み」を AI（周7）より前に出す**
     - 設計書13章に「過去のExcelもCSVで取り込めば、初日から履歴のあるカルテになり、AIも早く試せる」とあるとおり、週間教育177件・部下メモ96件・ロープレ120件の過去データは、周8（一番最後）よりも、**カルテ第1版や周7のAIレポートを試す前**に入っていたほうが、本人に「実際の履歴が入った画面」で確認してもらえます（ロープレ・部下メモの過去分は周3のあと、週間教育の過去分は周5のあと、または周5の直後に3つまとめて取り込む案）。

## 論点2：集める画面をいつ作るか
- 結論（案A／案B／別の案）：
  - **別の案（案Aと案Bの折衷：「周3のあと」と「周6のあと」の2回に分けて、それぞれ1本で作る）** を提案します。

- 理由：
  1. **案A（毎周少しずつ育てる）と案B（周6のあとにまとめて作る）の弱点**
     - 案Aだと、毎周カルテやホームのファイルを書き換えることになり、並列作業で一番避けたい「同じファイルの競合」が起きやすくなります。また毎周カルテの再確認が必要になります。
     - 案Bだと、周6が終わるまで「入力画面」ばかりが続き、アプリの中心であるカルテやホームを本人が見るのが遅くなります。また、カルテに並べて初めて気づく手直しが最後まで分かりません。
  2. **2回に分ける案（周3のあと＋周6のあと）の動き**
     - **1回目（周3の直後・並列にせず1本で作る）：「カルテ第1版 ＋ リーダー用ホームの第1版」**
       - 周3までに揃った「KPI・ロープレ・部下メモ」だけを並べたカルテと、リーダーのホーム（未達の一覧・部下メモの確認日・ロープレの知らせ）を作ります。ここで「カルテの見た目と使い勝手」を先に固めます。
     - **周4〜周6の間は、集める画面を触らない**
       - 一般日報（周4）・週間教育と管理画面（周5）・責任者日報（周6）を作るときは、それぞれの入力・一覧画面だけを作り、カルテやホームのファイルは触りません。これで周5の並列作業も邪魔されません。
     - **2回目（周6の直後・並列にせず1本で作る）：「集める画面の完成（カルテ完成版・ダッシュボード・全役割のホーム）」**
       - 周4〜周6で作った「一般日報（約束・見込み・受注・良かった人）」「週間教育」「責任者日報（打ち手・日々のMVP）」をまとめてカルテ・ダッシュボード・ホームにつなぎます（ダッシュボードは「関わった受注・粗利の達成率・チームの見込み」など周4の一般日報のデータを使うため、ここでの作成がぴったり合います）。

## 論点3：全体で並列にできる組・できない組
- 結論：
  - Claude Code の表にある3つの組（**① KPI と部下メモ**、**② 週間教育と管理画面の残り**、**③ 自動化と過去の記録**）は、すべて**並列にできます**。
  - ただし、どの周でも **「データベースの表（マイグレーション）・権限の守り（RLSと守りのテスト）・架空データ（`fixtures/`）・左メニューの空枠」だけは並列にせず、その周の先頭で1本で作ってから、画面と業務処理を2本で並列にする** のが安全です。

- 理由：
  1. **表にある3つの組の評価と注意点**
     - **組①：KPI と 部下メモ（周3） → できる**
       - 使う表が完全に別（`kpi_entries` 等 vs `subordinate_memos` 等）で、互いの結果も使いません。
       - 注意点として、部下メモには「メンバー本人に絶対に見せない」という重要な守りのテストがあり、また両方でデータベースのマイグレーションや架空データを同時に足すと番号がぶつかります。そのため、**表の定義と守りのテストだけを先に1本で通し、そのあと「KPIの画面・取り込み」と「部下メモの画面」を2本で並列**にするのが確実です。
     - **組②：週間教育 と 管理の画面の残り（設定値・監査ログ）（周5） → できる**
       - 使う表（`trainings` 等 vs `settings, audit_logs`）も、使う人（リーダー vs 管理者）も、画面の場所も完全に分かれており、並列に最も向いている組です。
       - ※なお、論点3の文中にあった「週間教育と研修」の組み合わせでも表は別なので並列自体は可能ですが、論点1のとおり「研修の記録」は周4（一般日報）より前に作っておくほうが順番として自然です。
     - **組③：自動化（ブラウザ自動操作・通知）と 過去の記録の取り込み（周8） → できる**
       - 自動化は外側の自動取得・通知の仕組み、過去の記録はデータ移行の処理であり、どちらも画面のコードをほとんど触らないため、競合の心配なく並列にできます（過去の記録だけ先に前倒しする場合も、他の画面作業とぶつかりにくい作業です）。
  2. **ほかに並列にできる組**
     - **KPI の中を2本に分ける案（もし周3の KPI が大きすぎる場合）**：KPI には「① CSV取り込み・承認・名前とチームの対応表」「② 月初の目標入力」「③ 未達の一覧と対応記録」の3つがあります。表とKPI計算の共通関数を先に1本で作れば、「① 取り込み・承認（管理者向け）」と「② 月初の目標入力（メンバー向け）」は画面も使う人も別なので2本で並列にできます。
  3. **絶対に並列にすべきでない組**
     - **「一般日報」と「責任者日報」**：責任者日報は、一般日報で入れた「見込みの数のチーム合計」や「良かった人」を並べるため、必ず順番に作る必要があります。
     - **「AIレポート（本人版）」と「AIレポート（指導版）」**：同じ集計・AI呼び出しの土台を使ううえ、「本人版からは部下メモと責任者日報をプログラムで確実に除く」という守りのテストが要になるため、必ず1本でまとめて作るべきです。
     - **すべての周の「表の定義（マイグレーション）・架空データ・守りのテスト」**：通し番号や外部キーの整合性が崩れるため、画面の並列から切り離して先に1本で行います。

## 論点4：途中で止めて確かめる所
- 結論：
  - **「毎周の終わりの短い画面確認（5〜10分）」** とは別に、実際に数日触って使い勝手を確かめる **「大きな確認（使ってみる節目）」は、全部の周ではなく「3か所」に絞る** のがよいと考えます。
  - 設計を見直す可能性が高い「危ない所」は、**① 一般日報（スマホでの入力量と流れ）、② KPI・受注の集計ルール、③ AIの効果判定、④ 周1の Microsoft 365 ログインと権限（RLS）** の4か所です。

- 理由：
  1. **止めて確かめる「3つの節目」**
     - **節目①：周3＋カルテ第1版が終わった所（リーダー層に実際に触ってもらう）**
       - ロープレ・部下メモ・KPI取り込み・カルテ第1版が揃った段階です。メンバー全員を巻き込む前に、本人とリーダー2〜3人で「カルテで1人の様子がすぐ掴めるか」「ロープレと部下メモの入力に迷わないか」を確かめます。
     - **節目②：周4（一般日報）が終わった所（スマホで実際に1日分を書いてみる）**
       - メンバー20〜50人が毎日使う画面なので、ここだけは次の周に進む前に、スマホとPCで「業後に何分で書けるか」「項目の並びに無理がないか」を本人に確かめてもらう価値が大きいです。
     - **節目③：周6（責任者日報）＋集める画面（完成版）＋周7（AI）が揃った所（1週間の流れを通して試す）**
       - 月曜朝のAI提案 → 週間教育 → 日々の日報 → 週末の振り返りという「1週間の輪」がつながったかを確かめます。
  2. **設計を見直すかもしれない「危ない所」と事前の備え**
     - **危ない所①：一般日報（周4）の欄の多さとスマホ表示**
       - 約束・リスト・見込み（前夜の予定／当夜の実績）・採用と訪問・受注（1件ずつ）・良かった人・週の最後・月末など、条件によって出る欄がいちばん多い画面です。紙の設計では良くても、スマホで触ると「前夜の予定と当夜の実績のどちらを入れているか分かりにくい」「縦に長すぎる」といった見直しが出やすい所です。
       - **備え**：周4は1回で全部を詰め込まず、「毎日の基本の入力」と「受注・週の最後・月末の追加欄」の2段階に分けて確認すると手戻りが小さく済みます。
     - **危ない所②：KPI・順位・受注の集計ルール（周3〜周4）**
       - 「アポだけの人の目標」「受注の3つの形（個人は関わった受注1件、チーム合計は二重に数えない）」「異動した人の過去データは当時のチームで集計する」など、細かい条件が重なります。
       - **備え**：画面のコードの中に計算を書かず、計算だけの部品（関数）を独立させ、架空データ（異動あり・アポだけの人・アポ絡み受注あり）を使った自動テストを画面より先に通します。
     - **危ない所③：AIの効果判定とデータの除外（周7）**
       - 2週間前後のチーム平均との比較や「コール数不足（判断できない）」の分岐、本人版からの部下メモ・責任者日報の除外は、AIプロンプトではなくプログラム側の正確さが求められます。
       - **備え**：「判定の計算とデータ除外のテスト」を先に固め、AIの文章の調整はあとからいつでも変えられるように分けて作ります。
     - **危ない所④：E 土台（周1）の Microsoft 365 ログインとデータベースの権限設定**
       - 会社の Microsoft 365 側の設定や、Supabase のデータベース段階での権限絞り込み（期間つきのMGR担当チームなど）は、外部サービスとのつなぎ込みで最初に詰まりやすい所です。今の計画どおり、周1でここだけに絞って先に確かめるのが最も安全です。

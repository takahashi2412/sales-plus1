# 回答：parallel-dev_v1
回答日：2026-10-27 ／ 回答者：Antigravity（Gemini 4 Argon）

## 論点1：並列は、このPCでどう動くか
- 結論：
  - Claude Code の考えに賛成です。並列で動かす場合は、**エージェントごとに別のワークツリー（別フォルダ）・別のブランチ（例：`task/roleplay-screen`、`task/talk-list`）に分け、同じフォルダで同時に書き換えないこと**が前提になります。
  - 作業結果も、親エージェントが勝手に1本にまとめるのではなく、**「1つの計画ファイル＝1つの作業ブランチ＝1つの報告書」**のまま止め、Claude Code が1本ずつ本線（`main`）との差分をレビューし、本人のOKのあとに本線へ取り込む今の流れに合わせるのが最も安全です。

- 理由：
  1. **Antigravity の作業場所の仕組み**
     - Antigravity で複数のエージェントを動かす方法は大きく2つあります。
       - **方法A（1つのチャットからサブエージェントを起動）**：親エージェントが `invoke_subagent` ツールで複数のサブエージェントを同時に起動します。このとき `Workspace` の設定で、`inherit`（親と同じフォルダ・既定値）、`branch`（複製した別フォルダ）、`share`（Git のワークツリーに相当する、リポジトリを共有した別フォルダ）の3種類を選べます。
       - **方法B（別々のチャット／Worktree で起動）**：Antigravity の画面からワークツリー（New Worktree）または別セッションを分け、それぞれに計画ファイル（`/plan`）を渡して動かします。
     - `inherit`（同じフォルダ）のまま複数エージェントを動かすと、1つのフォルダでは同時に1つの Git ブランチしか開けないうえ、ファイルの同時編集を自動で防ぐロック機構もないため、上書きや競合が起きます。そのため、並列時は別ワークツリー・別ブランチに分ける必要があります。
  2. **同じファイルを同時に書き換えないための決まり**
     - 別のワークツリー・別のブランチに分けても、2つのエージェントが同じファイル（左メニュー、ルーティング設定、`package.json`、共通の型定義など）を別々に編集すると、あとで `main` に取り込むときに競合（コンフリクト）が起きます。
     - これを防ぐには、システム上のフォルダ分離だけでなく、**計画ファイルの段階で「触ってよいフォルダ・ファイルの範囲」をエージェントごとに分け、共通ファイルは並列の前に1本で作っておく決まり**が要ります。
  3. **本線に出す流れとの相性**
     - 各エージェントが自分の作業ブランチにコミットし、報告書（`docs/reports/report_タスク名_v1.md`）を別名で出力して完了すれば、Claude Code は今までとまったく同じ手順で1本ずつ差分レビューと本線への取り込みができます。

- この環境で確かめたこと／確かめていないこと：
  - **確かめたこと**：
    - Antigravity の `invoke_subagent` ツールの仕様として、ワークスペース分離オプション（`inherit` / `branch` / `share`）が備わっていること。
    - `C:\Workspace\apps\sales-plus1` の設計書（`project-dashboard_v22.html`）および開発ルール（`CLAUDE.md`）の構成。
  - **未確認のこと**：
    - このPC（Windows 11）の `C:\Workspace\apps\sales-plus1` で、実際に UI の「New Worktree」やサブエージェントの `share` / `branch` を実行したときに、どのパスにフォルダが作られるか、ブランチ名がどう付くか、サブエージェント終了後にコミットやブランチがどう残るかは**未確認**です（ツールの仕様上、サブエージェントを強制終了すると `branch` ワークスペースが削除される仕組みがあるため、完了後の残り方は本番作業の前に小さなテストで1回確かめる必要があります）。
    - このPCには Node.js・npm・Docker・PostgreSQL が未インストール（2026-10-27 時点）のため、複数ワークツリーを作った際に `node_modules` やテスト実行環境がそれぞれのフォルダでどう動くかも**未確認**です。

## 論点2：E と A のどこを並列にするか
- Claude Code の仕分けに：一部ちがう（基本方針と3つの判定ルールには全面賛成。A の画面の分け方だけ、3本ではなく2本にまとめる案を提案します）

- 理由・別の案：
  1. **「E 土台」と「A：ロープレの表（データ）」を並列にしない（1本ずつ順番に進める）点：全面賛成**
     - E（Microsoft 365 ログイン・名簿・権限・守りのテスト）と、A の表（`roleplays`・`roleplay_themes`・`member_themes`・`talks`・`masters`・`settings`）は、すべての画面が使う土台です。判定ルール1「ほかの作業の結果が要るか」が「はい」になるため、ここを1本ずつ順番に固めるのは必須です。
  2. **「A：記録の画面／テーマ表と卒業の知らせ／トーク一覧」の分け方：3本ではなく「2本」にする提案**
     - 設計書（`project-dashboard_v22.html` セクション5「ロープレの形」）を見ると、次のつながりがあります。
       - **記録の画面 と テーマ表・卒業の知らせ**：「ロープレを入力するときに練習中のテーマが自動で入る」「○が2回続いたら卒業の候補を知らせ、実行者が卒業にする」という動きで強くつながっています。別々に作ると、卒業候補の判定や練習中テーマの扱いで食い違いが起きやすくなります。
       - **記録の画面 と トーク一覧**：記録画面から「使ったトークを選ぶ」「新しい言い方を書くとトーク一覧に『確認待ち』で入る」というつながりはありますが、いずれも `talks` テーブルの読み書きルール（API／クエリ）を先に決めておけば、画面自体はきれいに分けられます。
     - そのため、次のように進める案を提案します。
       - **手順①（先に1本）**：A の表（データベース・権限の守り・架空データ）を作るときに、**共通の型定義・画面の枠（左メニューと空のページルート）・共通の見た目部品**まで一緒に1本で作る。これで後の作業が共通ファイルを触らずに済みます（判定ルール2の徹底）。
       - **手順②（ここで2本並列）**：
         - **1本目**：「ロープレ記録の画面 ＋ テーマ表と卒業の知らせ」（密接につながるため1本にまとめる）
         - **2本目**：「トーク一覧の画面（一覧・絞り込み・試行中／標準の切り替え）」
       - これなら論点3の「最初は2本まで」とも合い、画面間の手戻りも防げます。
  3. **そのほか並列にできる所・すべきでない所**
     - **並列にできる所（A の次の周以降）**：「部下メモの画面」と「研修の記録の画面」、あるいは管理画面の「監査ログ画面」と「設定値の画面」のように、参照する主な表が別で、単体で動作確認できる画面どうし。
     - **並列にすべきでない所**：
       - **データベースのマイグレーション・架空データ（`fixtures/`）・守りのテスト**：通し番号や権限の整合性が崩れるため、必ず1本ずつ順番に行う。
       - **メンバーカルテ・ホーム（今日やること）・責任者日報・ダッシュボード**：複数の業務の記録を1画面に集めて並べる画面は、元になる業務ができてから1本で作る。

## 論点3：レビューと確認の量をどう抑えるか
- 結論：
  - 並列の数は **「最初は2本まで（E と A の表までは1本ずつ）」** に賛成です。
  - この開発では、代表が本業の合間に確認するため、「実装の時間」よりも「レビュー・本人確認の待ち時間と差し戻し」が1周の日数を左右します。本人が1回で無理なく確かめられる量（2画面まで）に絞るのが効果的です。

- 理由・工夫：
  1. **レビューを楽にする工夫（Claude Code 向け・本人向け）**
     - **計画ファイルで「変更してよいファイル・フォルダ」を縛る**：計画ファイルに「変更してよいのは `src/features/talks/` と報告書のみ。`package.json`・共通メニュー・DB定義・守りのテストは触らない」と明記します。Claude Code は最初に変更ファイル一覧を見るだけで、範囲外の書き換えがないかをすぐ確認できます。
     - **報告書に「本人が画面で確かめる手順（3〜5行）」を追加する**：Claude Code 案の3項目（変更したファイル・テストの結果・決められずに止めたこと）に加えて、**「誰でログインし、どこを押して、何が見えればOKか」**を短く書かせます。本人が触って確かめる負担を減らせます。
     - **報告書ファイル名を分ける**：報告書が競合しないよう、`docs/reports/report_タスク名_v1.md` のように計画ファイルと1対1の名前にします。
  2. **並列にしたときに起きやすい失敗と防ぎ方**
     - **失敗①：共通ファイルの競合（左メニュー、ルーティング、`package.json`）**
       - 防ぎ方：並列に入る前の1本で、必要なパッケージの追加と、左メニュー・空の画面ルートまで作っておき、並列の各エージェントには自分の画面フォルダの中だけを書かせます。
     - **失敗②：画面ごとの見た目・ルールのズレ**
       - 防ぎ方：別々のエージェントが同時に画面を作ると、余白や色（「Rush up 資料デザイン」の赤の使い方・▲▼の表記・影なし等）が微妙にズレやすくなります。最初の1画面（または共通部品）でデザインのお手本を確定させてから、それを参照して並列で作らせます。
     - **失敗③：1本目の修正が2本目に波及する**
       - 防ぎ方：2本同時に作って1本目のレビューで「共通の書き方を変えよう」となると、2本目も同じ直しが必要になります。初めてのパターン（最初の入力画面など）は1本で先に通し、型が固まった2画面目・3画面目で並列を使うと差し戻しが減ります。
     - **失敗④：古い `main` からの分岐やワークツリーの取り違え**
       - 防ぎ方：「2本を同時に分岐したら、2本とも本線に取り込んで片付けるまで次の並列は始めない」というルールにします。

## そのほか気になったこと
1. **今の段階（E 土台の試し）では、まず1本で開発環境と流れを確かめるのが安全**
   - 現在このPCには Node.js・npm などが未インストールであり、まずは「E 土台の試し」で環境を整え、「計画ファイル → Antigravity で実装・テスト → Claude Code でレビュー → 本人確認」の基本の1周を回す段階にあります。
   - E 土台と A のデータ表はもともと並列にしない部分なので、**そこまでは今までどおり1本ずつ進め、A の画面に入る直前に、Worktree（またはサブエージェントの `share`）でブランチとフォルダがどう動くかを小さく1回試す**のが、手戻りがなく確実です。
2. **「別々の Worktree チャット」と「1チャット内のサブエージェント」の使い分け**
   - Antigravity 内で親エージェントがサブエージェントを複数呼ぶよりも、Claude Code が計画ファイルを2本（例：`plan_roleplay-screen_v1.md` と `plan_talk-list_v1.md`）作り、それぞれ別の作業ブランチとして独立して動かしてコミット・報告書出力まで行わせるほうが、「Claude Code が設計・レビューし、Antigravity が実装する」という役割分担がシンプルに保てます。どちらの手順がこのPCで扱いやすいかも、A の画面に入る前の小さなテストで確かめるのがよいと考えます。
